# 客厅 → 主卧掉帧诊断

范围：用户反馈电脑端、全屋大致加载完成后，进入主卧掉帧。基线 main / 8fcd1e1。以下前半部分记录初始诊断；用户随后明确选择取消所有碰撞并大幅简化床品，实施结果见文末。

## 最明确的热点：行走碰撞

`src/main.js:85` 的 allowedStep 使用全模型世界包围盒粗筛，再对候选原始网格做九条射线精确检测。斜向移动最多做两次 allowedStep，即十八条水平射线，另有地面检测。没有运行时 BVH。主卧边界附近的“主卧柜背斜接墙”有 16,820 个三角形，“Natural cane insert”有 50,264 个三角形。

用原 GLB 解码几何与变换重建场景，直接执行当前 allowedStep 函数。每个探针方向测 35 次取中位数：

| 探针位置 (x,z) 与方向 | 当前查询 | BVH 对照 |
| --- | ---: | ---: |
| (11.70,3.45)，朝 -Z | 4.9862 ms | 0.0475 ms |
| (10.95,3.90)，朝 +Z（受阻） | 4.1186 ms | 0.0247 ms |
| 客厅落点 (11.70,5.10)，朝 -Z | 0.0110 ms | 0.0169 ms |

这是 Node 中单次轴向碰撞查询的 CPU 耗时，不是整帧耗时，也不是用户浏览器 FPS。它确认了具体位置存在可消除的 CPU 热点，但未完整重现用户行走轨迹。60 FPS 的单帧预算是 16.67 ms，这一热点足以占用有意义的预算。

对照只在测试场景为 62 个高面数网格建立 indirect BVH，不减面、不改原始索引。238 个采样位置 × 四个方向，952 次通行结果比较全部一致。此检查不替代门窗开合、家具变化、延迟加载的完整回归。同步构建 BVH 约 202 ms，生产接入必须提前离线生成、使用 worker 或分帧准备，不能把这段同步工作放到行走帧里。仓库既有约束将 BVH 限于烘焙工具；此轮对照没有改变该约束或添加运行时依赖。

## 渲染还有浪费，但尚无 GPU 归因

实际解码共 1,493 个 mesh、1,116,159 个三角形。两间卧室床品各 149,995，室外模块 380,180。压缩后的下载 MB 数不等于逐帧渲染工作量。

当前仅有视锥剔除，没有房间/门洞遮挡剔除；模块加载后持续留在场景中。16:9、65 度视野、近似默认落点朝向的几何视锥估算：

| 视点 | 视锥相交 mesh | 三角形 |
| --- | ---: | ---: |
| 客厅 | 895 | 608,689 |
| 主卧 | 579 | 553,495 |

主卧视锥内包括次卧床品 149,995 个三角形及室外几何 190,090 个三角形。墙壁能通过深度测试遮住最终像素，但项目没有提前在房间级跳过这些物体的渲染提交。以上不是 renderer.info 的真实 draw call 统计。主卧估计总量比客厅低，所以不能仅用这些数字断言主卧 GPU 更慢；具体像素覆盖、材质、透明物体与分辨率仍需浏览器 profile。

桌面自动分辨率上限为 DPR 1.7（设备 DPR 达到上限时约为 DPR 1 的 2.89 倍像素）；只有平滑帧时长超过 30 ms 才降档，每 180 帧检查一次，最低降至 1。它无法及时应对 60 FPS 降至 40–50 FPS 一类问题。

## 优先顺序

1. 加速精确碰撞查询，保持原几何/家具阻挡/门洞语义。若使用 BVH，安排预构建并覆盖交互与延迟挂载回归；也可给建筑与家具提供经过验证的独立碰撞代理。
2. 用实际浏览器在重复路线记录移动 CPU、渲染提交、GPU、帧时间及 renderer.info，区分行走与原地转头。先测 DPR 1 对照，再决定是否修改自动分辨率策略。
3. 用门洞可见性/保守房间集合减少墙后提交，保留窗外可见物；不能直接隐藏除当前房间以外的全部模块。
4. 在得到性能余量后提高模型质量：近看家具与床品保留精度，远处/室外使用 LOD，重复零件按材质及交互边界批处理。不要再次对已减面的床品盲目减面。

初次加载的暂停机制确实存在（目标房间未完成就直接 return），但与用户这次描述不优先匹配。

复现：`node scripts/audit-navigation-performance.mjs`。原始输出见 `navigation-performance.json`。不同硬件、JIT 与系统负载会改变时间。

## 按用户选择实施

- 取消全部行走碰撞及户型边界限制，允许穿墙和家具。保留固定 1.5 m 眼高、房间导航、目标房间加载等待及交互状态。移除障碍包围盒维护与射线查询；房间标签只在房间变化时更新。
- 按用户要求使用 Blender 4.5.14 LTS，从减面前的原模块重组全屋并导入，六个床品对象合并重合顶点后保留非破坏性 Decimate COLLAPSE 0.2 修改器。两间卧室共 299,990 → 59,992 个三角形（约 -80%）。导出时只接入六个对象的新几何及 UV/法线，原模块的材质、贴图和节点层级保留。各对象局部包围盒边界变化小于 1 mm；这不代表完整表面误差。
- 10 个其他模块和 62 个共享贴图不变。重新从运行模块精确组装全屋源几何，重新烘焙地面、墙面、照明和物体接触数据；没有伪造版本清单绕过失效检查。
- 所有模块的 1,493 个 mesh 解码数据、索引、节点变换与组装烘焙源一致，GLTF 验证 0 errors。构建通过，总模型/贴图/光影资源 9,090,874 字节，小于 20 MB。
- Chrome / Apple M4 硬件渲染，1100×760、DPR 1，保留启动和编译流程。两间卧室默认落点截图检查未见此前明显破洞，无页面或 shader console errors。抓图时暂停动画并即时渲染，画面对照不代表手机帧率。
- 主卧同机位 renderer.info：836 draw calls 不变，三角形处理 1,193,690 → 761,694（约 -36.2%，含渲染通道重复处理）；次卧 330,994 → 210,995。尚未做房间遮挡/批处理，因此 draw calls 未降低。
- 浏览器中 120 次自由行走步进，从 (11.7,1.5,4) 到 (11.7,1.5,1.3)，不再被墙体阻挡。浏览器同步 CPU 热点探针中，原版 move 中位数约 5.5 ms；新版单次低于计时精度，120 次实际步进合计约 0.9 ms。不能把这个结果换算成整页 FPS。原始数据见 browser-performance.json。

重现：从 8fcd1e1 保留原始 modules，先用 assemble-modules.mjs 组装原始 GLB；运行 Blender 的 blender-simplify-bedding.py，再用 import-blender-bedding.mjs 接回模块；用 assemble-modules.mjs 组装最终烘焙源，再依次运行三个 bake 脚本，执行 verify-modules.mjs、npm run build 和 check-model-budget.mjs。不要把已简化输出再次作为源输入。浏览器检查脚本通过 HOME_DECO_PLAYWRIGHT 指向独立安装的 Playwright，不添加生产依赖。

浏览器复测曾因 Vite 给模块 URL 附加时间戳、测试拦截器没有匹配查询参数而超时；修正诊断脚本的 URL 匹配后，未跳过生产加载/编译流程的最终检查通过。这不是生产加载失败。

可编辑文件 source/home-deco-bedding.blend 是从运行 GLB 重建的场景，包含原床品及减面修改器与打包贴图，不是原作者未入库的 .blend。该本地文件按仓库既有规则忽略，重建脚本保留在仓库。最终模型几何由 Blender 生成，网页光影仍由项目既有离线烘焙脚本生成。
